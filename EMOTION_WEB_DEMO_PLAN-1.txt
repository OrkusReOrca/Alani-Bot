--------------------------------------------------------------------------------
0. GOAL IN ONE PARAGRAPH
--------------------------------------------------------------------------------
Add a password-protected web dashboard, served by the SAME Python process that
already runs on the bot-hosting.net "Alani Emotion" slot (emotion-service/main.py),
so the user can open it from any computer (e.g. a university PC) during their
thesis defense: log in, upload (or pick) a short video of themselves, watch
processing progress, then see a polished results page (circumplex quadrant,
annotated frame, AU bars, transcript, voice/gaze/head stats, timings, prompts).
It must work with ZERO infrastructure change: same slot, same startup file
(emotion-service/main.py), same env-var mechanism, same requirements.txt style.
The existing Discord flow (".a emo ...", POST /run, POST /resend) must keep
working exactly as it does today.

The thesis is no longer "real-time". A run finishing within ~10 minutes is fine
(user records at the start of the talk, presents, checks results at the end).

--------------------------------------------------------------------------------
1. HARD CONSTRAINTS (do not violate)
--------------------------------------------------------------------------------
C1. No new infrastructure: no new hosts, no tunnel, no database server, no
    reverse proxy, no second slot. Everything runs inside the existing
    main.py process, storing data on the slot's own disk (EMOTION_DATA_DIR).
C2. No native-compile dependencies (bot-hosting.net's build wall; see root
    README "Daily jobs" and emotion-service/README.md "Why no OpenFace").
    Prefer ZERO new pip deps. If one is truly needed it must be pure-Python /
    prebuilt-wheel. Preferred design below needs none.
C3. bot-hosting.net serves plain http://IP:PORT. NO HTTPS. Consequences:
    - Browser getUserMedia/MediaRecorder will NOT work (needs secure context).
      So do NOT build an in-page "Record" button as the primary path.
      Primary path = file upload. On phones/tablets, <input type="file"
      accept="video/*" capture="user"> opens the native camera app and works
      over http. On desktop it is a normal file picker (user records with
      Windows Camera / phone, then uploads).
    - Do NOT set the "Secure" cookie flag (cookie would never be sent).
    - Passwords travel in cleartext. Acceptable for a throwaway demo password;
      document that the user must use a unique demo password, not one reused
      anywhere else.
C4. The uni network may block CDNs / non-standard ports. The frontend must be
    fully self-contained: no CDN scripts, no Google Fonts, no external images.
    Charts are hand-written inline SVG/CSS. No build step (no npm, no bundler).
C5. Python version on the host is unknown (dev container here is 3.13). Stdlib
    `cgi` was removed in 3.13, so DO NOT rely on cgi.FieldStorage. Do not use
    3.12+-only syntax either. (See upload design in 4.2: raw-body upload, no
    multipart parsing at all.)
C6. RAM is the main risk (torch + py-feat + faster-whisper + openSMILE in one
    small slot). Therefore: exactly ONE heavy job at a time, process-wide
    (shared with Discord-triggered runs). Never load a second detector.
C7. Keep the repo's existing style: heavy explanatory docstrings, small
    modules, plain config.py env reading via _required(), stdlib http.server
    (no Flask/FastAPI unless unavoidable).

2. WHAT EXISTS TODAY (facts verified by reading the code)
--------------------------------------------------------------------------------
main.py       ThreadingHTTPServer, only do_POST. Routes /run and /resend, both
              guarded by "Authorization: Bearer <EMOTION_SERVICE_SECRET>".
              Refuses to start if EMOTION_SERVICE_SECRET unset.
pipeline.py   resolve_clips(run_mode) (Drive listing) and run_clips(...).
              _process_clip(...) is the real work, but it is TIED to Drive and
              Discord: it downloads from Drive, truncates to 120 s, extracts
              up to 32 frames, runs ONE shared py-feat pass (detector.py) for
              AU + gaze + head pose, extracts audio, faster-whisper transcript,
              openSMILE voice string, builds the two ValAro prompts
              (prompt.py), calls OpenRouter twice (openrouter_client.classify,
              frames as image_url blocks, max_tokens=8), combines to a
              quadrant (PA/NA/ND/PD), writes cache JSON + CSV row, renames the
              Drive file DONE_*, then POSTs a callback to Alani-Bot.
store.py      Per-clip JSON cache keyed by Drive fileId in DATA_DIR/clips/,
              first-frame JPG, append-only CSV DATA_DIR/clips_log.csv.
prompt.py     build_prompt_valence/arousal, parse_*, combine(), SHORT_CODE.
              Quadrant only - there is NO continuous valence/arousal score.
visualize.py  render_annotated_frame(detection_row, dest) via py-feat
              plot_detections (box, landmarks, AU bars, pose, gaze).
config.py     LISTEN_PORT (EMOTION_LISTEN_PORT or SERVER_PORT or 8000),
              MAX_CLIP_SECONDS=120, MAX_VLM_FRAMES=32, WHISPER_MODEL=small.
video.py      truncate_if_needed, extract_frames, make_thumbnail, extract_audio.
Modalities    AU, T (transcript), VO (voice), ET (eye gaze), HT (head pose).
Cache modes   "d" = extract+cache all 5 regardless; "s" = only requested.
No Python tests exist in the repo.

3. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
Browser (uni PC)  --http-->  main.py (same process, same port)
   GET  /                    -> redirect to /app (or login)
   GET  /app/*               -> static files from emotion-service/web/
   POST /api/login           -> sets signed session cookie
   POST /api/upload          -> raw-body video upload -> creates a Job
   GET  /api/jobs            -> list jobs (newest first)
   GET  /api/jobs/<id>       -> job status + result (poll every ~1.5 s)
   POST /api/jobs/<id>/rerun -> re-run VLM step with other modalities
   POST /api/jobs/<id>/pin   -> pin / unpin (exempt from auto-delete)
   DELETE /api/jobs/<id>     -> delete job + its files
   GET  /api/jobs/<id>/media/<name> -> frame/annotated image, video (auth'd)
   POST /api/warmup          -> background-load models
   GET  /api/health          -> unauthenticated, tiny {"ok":true} (reachability test)
   POST /run, /resend        -> UNCHANGED (bearer secret, used by Alani-Bot)

One global JobRunner thread + queue.Queue executes jobs sequentially. The
Discord-triggered pipeline.run_clips ALSO takes the same global lock so the two
paths can never overlap (C6).

4.2 Upload design (no multipart, no new deps)
---------------------------------------------
Client: fetch/XHR POST /api/upload with the raw File as body.
  Headers: Content-Type: application/octet-stream
           X-Filename: <encodeURIComponent(original name)>
           X-Modalities: "AU.T.VO.ET.HT" (dot list, same grammar as Discord)
           X-Cache-Mode: d|s
  Use XMLHttpRequest (not fetch) so upload progress events drive a progress bar.
Server: read exactly Content-Length bytes in 1 MiB chunks, streaming to
  DATA_DIR/web/jobs/<jobid>/input.<ext>. Reject:
    - missing/oversized Content-Length (limit EMOTION_WEB_MAX_UPLOAD_MB,
      default 300) -> 413
    - extension not in drive._VIDEO_EXTS (.mov .mp4 .avi .mkv .webm) -> 415
    - not authenticated -> 401
  Sanitize filename (basename only, strip control chars, cap 120 chars); the
  on-disk name is always input.<ext>, the original name is only metadata.
  After the upload: ffprobe-equivalent sanity check via video.get_duration_and_
  frame_count; if unreadable -> job fails fast with a friendly error.
  Truncation to MAX_CLIP_SECONDS (120) is applied exactly as today and the UI
  must SAY so ("Only the first 2:00 of your clip is analysed").
Return 201 {"jobId": "...", "queuePosition": n}.
Persist the uploaded input.<ext> so reruns/toggles do not require re-upload.

4.3 Source-agnostic core (the only real refactor)
-------------------------------------------------
Extract from pipeline._process_clip a function:

  core.process(clip_id, src_path, modalities, cache_mode, more_info,
               progress, work_dir) -> dict result

It performs everything from "truncate -> frames -> detection -> audio ->
transcript/voice -> prompts -> 2 VLM calls -> combine -> persist cache" and
returns a result dict containing at least:
  prediction (e.g. "Positive_Activate"), short ("PA"), valence, arousal,
  valence_raw, arousal_raw, valence_prompt, arousal_prompt,
  au_string, transcript, voice_string, eye_string, head_string,
  modalities_used, stage_timings {stage: seconds}, total_seconds,
  frame_count, clip_seconds, truncated(bool),
  files: {first_frame, annotated (optional)}
`progress(stage, detail=None)` is called at stage boundaries. Stage ids (fixed,
the UI maps them to labels):
  queued, truncating, frames, face (py-feat AU+gaze+pose), audio,
  transcript, voice, vlm_valence, vlm_arousal, finalizing, done, error
Rules:
  - core must NOT touch Drive, Discord callbacks, or rename anything.
  - The Drive path (pipeline._process_clip) keeps doing: download, call core,
    store.append_log_row, drive.mark_done, callback.post_result - identical
    observable behavior to today. Do a manual regression with ".a emo run1".
  - Web jobs use clip_id = "web_<jobid>" so store.py's per-clip JSON cache
    works unchanged and cannot collide with Drive fileIds.
  - For the web the annotated frame is ALWAYS produced (more_info=True
    equivalent) because the dashboard shows it; visualize failure still falls
    back to the plain frame.
  - Persist the 32 extracted frames (jpg) under the job dir so a rerun with
    different modalities skips frame extraction and detection entirely. Frame
    jpgs are small; keep them. (Today they are deleted with work_dir.)
  - Record per-stage wall-clock timings (time.monotonic) for the UI.
  - Detection result: py-feat dataframe is not JSON-friendly; the AU/pose
    strings in cache are what reruns need, so no dataframe persistence needed.
    Additionally persist a small JSON of numeric AU intensities, gaze and
    head-pose angles (for the dashboard bars/gauges) - add a helper in
    extract_au.py/extract_pose.py that returns the raw numbers it already
    computes before formatting them into strings (check what those functions
    return; reuse, do not recompute).

4.4 Jobs: model, persistence, runner
------------------------------------
Job JSON at DATA_DIR/web/jobs/<jobid>/job.json (atomic write: temp file +
os.replace). Fields:
  id, created_at (UTC ISO), original_filename, size_bytes, status
  (queued|running|done|error|interrupted), stage, stage_detail, modalities
  (list), cache_mode, parent_id (for reruns, else null), pinned (bool),
  result (dict from 4.3 or null), error (string or null), runs: [ ... ]
Reruns: POST /api/jobs/<id>/rerun {modalities:[...]} creates a NEW job whose
  parent_id=<id>, copying (hard link or copy) input + frames from the parent so
  only missing modalities are extracted and the VLM steps re-run. The UI shows
  all runs of the same source clip together as a comparison table
  (modalities -> prediction), which doubles as a live ablation demo.
Runner: single daemon thread, queue.Queue, global threading.Lock
  `heavy_lock` (in a shared module, e.g. runtime.py) acquired around core.process
  AND around pipeline.run_clips's per-clip work for Discord runs.
  On startup: scan jobs; any with status running/queued -> mark "interrupted"
  (UI offers a "Re-run" button). Never silently drop.
Errors: catch everything per job, store str(e) + short traceback tail
  (trimmed, no secrets), status=error. A failed job never kills the runner.
Retention: on startup and every hour, delete unpinned jobs older than
  EMOTION_WEB_RETENTION_HOURS (default 24) - uploaded face videos are
  personal data; the UI also has a "Delete this run" button and a footer note
  saying uploads are auto-deleted. Pinned jobs are exempt.
Spend guard: cap new jobs per rolling hour (EMOTION_WEB_MAX_JOBS_PER_HOUR,
  default 20) -> 429 with a friendly message. Prevents a leaked password from
  burning OpenRouter credits.
Disk guard: refuse upload (507) if free space on DATA_DIR < 2x upload size.

4.5 Auth (web_auth.py)
----------------------
- Env DEMO_PASSWORD. Unset -> web UI disabled (404), log once.
- POST /api/login {password}: compare with hmac.compare_digest. On success set
  cookie  `emo_session=<payload>.<sig>`  where payload = base64url(JSON
  {iat, exp}) and sig = HMAC-SHA256(key, payload). Key = EMOTION_WEB_SESSION_KEY
  if set, else derived from DEMO_PASSWORD + EMOTION_SERVICE_SECRET (so changing
  either logs everyone out). Attributes: HttpOnly; SameSite=Strict; Path=/;
  Max-Age=EMOTION_WEB_SESSION_HOURS (default 12). NO Secure flag (C3).
- Rate limit failed logins per client IP: 5 failures / 60 s -> 429 with
  Retry-After for 60 s. Use the socket peer address (also read X-Forwarded-For
  only if the first hop is clearly a proxy; otherwise ignore it). Small sleep
  (~0.5 s) on every failure.
- Every /api/* route except /api/login and /api/health requires a valid
  cookie. Static login page is public; the app shell requires auth (redirect to
  /app/login.html).
- POST /api/logout clears the cookie.
- CSRF: SameSite=Strict + require the custom X-Filename/Content-Type headers on
  state-changing routes; additionally reject state-changing requests whose
  Origin header is present and not equal to the request Host.
- Media route must also require the cookie (no public image URLs).
- Never log the password or cookie. Never echo secrets in errors.
- Bearer-secret routes /run and /resend are unchanged and independent of the
  cookie (and cookies must NOT grant access to them).

4.8 Models warm-up (runtime reality)
------------------------------------
Cold start dominates the first run (torch import, py-feat weights - possibly a
first-time download -, whisper weights). Provide:
  - Optional env EMOTION_WARMUP_ON_START=1 -> background warm-up thread at boot.
    Off by default (RAM spike on boot; user may prefer manual).
  - "Warm up models" button on Home (calls /api/warmup) and a status badge
    ("Models: cold / warming / ready") driven by a flag in runtime.py.
  - Demo-day instruction: warm up + run one throwaway clip before presenting.
Expected runtimes (ESTIMATES for a CPU-only shared slot, NOT measured; the
implementer/user should replace them with real numbers from one `mif` run):
  warm, 2-min clip, all modalities: ~3-6 min
  cold first run: ~4-8 min (+ model load / downloads)
  rerun with cached modalities: ~20-60 s (2 VLM calls with up to 32 images)
  shorter clip (30-60 s) roughly halves the heavy stages.
The UI must never imply a fixed ETA; show elapsed time and per-stage actuals.

4.10 Development without the heavy stack
----------------------------------------
The cloud/dev container does not have torch/py-feat/whisper. Make the web layer
importable and testable WITHOUT them: keep heavy imports lazy (they already are
inside detector/extractors) and add fake_pipeline.py selected by
EMOTION_FAKE_PIPELINE=1, which sleeps a few seconds per stage, calls progress()
exactly like the real core, and returns a canned result (include a generated
placeholder frame + annotated image, fake AU numbers, sample transcript). This
lets the UI, auth, queue, upload, rerun, retention and polling be developed and
verified end-to-end locally (python3 main.py with env vars, then drive it with
curl and a headless Chromium via Playwright; Chromium is preinstalled in the
cloud environment at /opt/pw-browsers - do not run `playwright install`).
Take screenshots of login, home, processing, result at desktop and phone width
to verify the design.

7. RISKS & OPEN QUESTIONS
--------------------------------------------------------------------------------
R1  RAM on the slot may be insufficient for torch+py-feat+whisper together.
    Mitigation: single heavy lock; whisper small/int8 already default; if it OOMs
    consider modality presets (AU+T) and unloading whisper after use (do not
    implement unless OOM is observed).
R2  Uni network may block the slot's port. Mitigation: health URL check, hotspot,
    recorded fallback. (No tunnel allowed by constraint C1.)
R3  Slot or proxy may cap request body size/time below 300 MB - recommend
    compressed 720p/1080p clips; make EMOTION_WEB_MAX_UPLOAD_MB lowerable.
R4  Slot restarts (bot-hosting.net) would kill an in-flight job: handled via
    "interrupted" status + rerun button; persisted inputs make this cheap.
R5  Runtime numbers are estimates. First action of the implementer/user:
    run one real clip and record real per-stage timings, then update 4.8.
